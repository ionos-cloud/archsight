# Import System

The import system allows you to declaratively define data imports that generate architecture resources from external sources like GitLab, GitHub, and git repositories.

## Overview

Imports are defined as YAML resources with kind `Import`. Each import specifies:

- A **handler** that knows how to fetch and process data
- **Configuration** specific to that handler
- Optional **caching** to avoid re-running unchanged imports

Dependencies between imports are automatically derived from the `generates` relation. When a parent import generates child imports, those children depend on the parent and will run after it completes. An import can also declare further dependencies with `import/dependsOn` (see [Dependencies](#dependencies)).

Besides the built-in handlers, a resources repository can bring its own (see [Importers of the Resources Repository](#importers-of-the-resources-repository)).

The import executor runs imports concurrently in dependency order, with a visual progress display showing completion percentage and ETA.

## Running Imports

```bash
# Run all pending imports
archsight import

# Verbose output
archsight import -v

# Show execution plan without running
archsight import --dry-run

# Force re-run all imports (ignore cache)
archsight import --force

# Run one import and the imports it depends on
archsight import -f Import:Deployments

# Run only that import, not its dependencies (with --force to ignore its cache)
archsight import -f Import:Deployments --no-deps --force

# Validate the resources after the run (like archsight lint)
archsight import --lint
```

With `--lint`, an error in a resource that an import wrote names that import (`(generated by Import:X)`): the import
in the resource's `generated/script`, else the import whose output file holds it. So a dangling reference between
generated files shows up with the import that caused it.

### Progress Display

In TTY mode, imports show a live progress display:

```
Overall ████████████░░░░░░░░ 60% [30/50] ETA: 2:15
Import:Repo:project-a - Analyzing code
Import:Repo:project-b - Cloning repository
Import:Repo:project-c - Done
```

## Defining an Import

Create YAML files in the `imports/` directory:

```yaml
apiVersion: architecture/v1alpha1
kind: Import
metadata:
  name: Import:MyData
  annotations:
    import/handler: <handler-name>
    import/priority: "10"
    import/cacheTime: "24h"
    import/config/key: value
spec: {}
```

### Core Annotations

| Annotation | Description |
|------------|-------------|
| `import/handler` | Handler to execute (required): a built-in one or one registered by `import/handlerPath` |
| `import/handlerPath` | Ruby file of a handler of the resources repository, relative to the resources directory |
| `import/dependsOn` | Imports that must run first: names or glob patterns, comma separated |
| `import/enabled` | Set to "false" to disable |
| `import/priority` | Execution order (lower runs first, default: 0) |
| `import/cacheTime` | Cache duration: "30s", "30m", "1h", "24h", "7d", or "never" |
| `import/outputPath` | Output file path relative to resources directory |

Settings every handler understands:

| Annotation | Description |
|------------|-------------|
| `import/config/inputs` | Files the import reads (glob patterns relative to the resources directory, comma separated); a change invalidates the cache |
| `import/config/requiredEnv` | Environment variables the import needs, comma separated; a missing one fails the import |
| `import/config/optional` | `"true"`: skip the import with a warning when a required variable is missing (it stays stale; its dependents run) |

### Caching

Imports can be cached to avoid re-running when data hasn't changed:

```yaml
import/cacheTime: "24h"  # Re-run after 24 hours
```

Supported duration formats:
- `30s` - 30 seconds
- `30m` - 30 minutes
- `1h` - 1 hour
- `24h` - 24 hours
- `7d` - 7 days
- `never` - Always run (default)

The cache uses the `generated/at` annotation written by handlers. When an import completes, it writes a marker with the current timestamp. On subsequent runs, the executor checks if `generated/at + cacheTime > now` to skip cached imports.

The cache is also invalid, and the import runs again, when:
- its output file (`import/outputPath`) or a file it recorded as its own (`generated/outputs`) is missing
- its handler or `import/config/*` settings changed (`generated/configHash`)
- a file matched by `import/config/inputs` changed (`generated/inputsHash`: paths, sizes, modification times)
- an import it declares in `import/dependsOn` executed in the same run (one served from the cache does not count).
  Child imports are not affected when their parent runs; they keep their own cache time.

### Dependencies

An import runs after the import that generated it. `import/dependsOn` adds more: import names or glob patterns,
comma separated.

```yaml
import/dependsOn: "Import:GitHub:acme, Import:Repo:*"
```

A pattern also covers imports that do not exist yet: the import waits for every import whose last run generated a
match, and on a first run for every import whose handler generates imports. So `Import:Repo:*` waits for the GitHub
import and then for the repository imports it creates. Declared dependencies are part of the execution plan (`-n`,
which also lists patterns without a match), of `-f` (a filtered import brings its dependencies along) and of the
cycle check. `archsight lint` reports a name that matches no import.

`--no-deps` runs only the imports `-f` matches: their dependencies neither run nor are waited for, so the import works
on the model as it is (re-importing thousands of repositories is not needed to try a change to one importer). The
cache still applies; add `--force` to run it anyway.

### Configuration Pattern

Handler-specific configuration uses `import/config/*` annotations:

```yaml
import/config/host: gitlab.company.com
import/config/fallbackTeam: "Team:Platform"
```

## Available Handlers

### gitlab

Lists repositories from a GitLab instance and generates child Import resources.

**Configuration:**
- `host` - GitLab host (required)
- `exploreGroups` - If "true", explore all visible groups (default: false)
- `repoOutputPath` - Output path for repository handler results
- `fallbackTeam` - Default team when no contributor match found (propagated to child imports)
- `botTeam` - Team for bot-only repositories (propagated to child imports)
- `corporateAffixes` - Comma-separated corporate username affixes for team matching, e.g., "ionos,1and1" (propagated to child imports)

**Environment:**
- `GITLAB_TOKEN` - Personal access token (required)

**Output:** Generates `Import:Repo:gitlab:*` resources for each repository.

### github

Lists repositories from a GitHub organization and generates child Import resources.

**Configuration:**
- `org` - GitHub organization (required)
- `repoOutputPath` - Output path for repository handler results
- `fallbackTeam` - Default team when no contributor match found (propagated to child imports)
- `botTeam` - Team for bot-only repositories (propagated to child imports)
- `corporateAffixes` - Comma-separated corporate username affixes for team matching, e.g., "ionos,1and1" (propagated to child imports)

**Environment:**
- `GITHUB_TOKEN` - GitHub Personal Access Token (required)
  - Create at: https://github.com/settings/tokens
  - Required scopes: `repo` (private repos) or `public_repo` (public only)
  - If you have `gh` CLI authenticated: `export GITHUB_TOKEN=$(gh auth token)`

**Output:** Generates `Import:Repo:github:*` resources for each repository.

### repository

Analyzes a single git repository and generates a TechnologyArtifact resource.

**Configuration:**
- `path` - Local repository path (required)
- `gitUrl` - Git URL to clone from (if not already cloned)
- `archived` - If "true", mark as archived
- `visibility` - Repository visibility: internal, public, open-source
- `sccPath` - Path to scc binary (default: scc)
- `fallbackTeam` - Default team when no contributor match found
- `botTeam` - Team for bot-only repositories
- `corporateAffixes` - Comma-separated corporate username affixes for team matching (e.g., "ionos,1and1"). Enables matching git usernames like `jsmith-ionos` or `ionos-jsmith` to team member "John Smith". Without this, corporate username pattern matching is inactive.

**Output:** Generates one TechnologyArtifact resource with:
- Code analysis metrics (languages, LOC, estimated cost)
- Git activity metrics (commits, contributors, bus factor)
- Team matching based on contributor history
- Deployment artifact detection (containers, charts, etc.)
- Agentic tool detection (Claude, Cursor, etc.)

**Special Cases:**

The repository handler creates minimal artifacts for repositories that can't be fully analyzed:

| Status | Reason |
|--------|--------|
| `inaccessible` | Clone failed due to access denied or auth errors |
| `empty` | Repository has no commits |
| `no-code` | No analyzable source code (only config, docs, etc.) |

These artifacts include `activity/status` and `activity/reason` annotations documenting why full analysis wasn't possible.

### rest-api-index

Fetches an API index JSON and generates child Import resources for each API.

**Configuration:**
- `indexUrl` - URL to fetch API index JSON (required)
- `baseUrl` - Base URL for spec files (optional, derived from indexUrl)
- `interfaceOutputPath` - Shared output path for ApplicationInterface resources
- `dataObjectOutputPath` - Shared output path for DataObject resources
- `skipVisibility` - Comma-separated visibilities to skip (e.g., "public-preview,beta")

**Expected Index Format:**
```json
[
  {
    "name": "compute",
    "version": "6.0",
    "visibility": "private",
    "specPath": "/rest-api/compute/openapi.yaml",
    "redocPath": "/rest-api/compute/redoc.html",
    "gate": "GA"
  }
]
```

**Output:** Generates `Import:RestApi:*` resources for each API in the index.

### rest-api

Downloads an OpenAPI spec and generates ApplicationInterface and DataObject resources.

**Configuration:**
- `name` - API name (required)
- `version` - API version (default: "1.0")
- `visibility` - API visibility (default: "private")
- `specUrl` - Full URL to OpenAPI spec - http, https, or file:// (required)
- `htmlUrl` - Full URL to HTML documentation (optional)
- `gate` - Release gate: "GA", "BETA", etc. (default: "GA")
- `interfaceOutputPath` - Output path for ApplicationInterface resources
- `dataObjectOutputPath` - Output path for DataObject resources

**Output:**
- ApplicationInterface resource with detected auth methods (JWT, Basic, API Key, OAuth2, OIDC)
- DataObject resources extracted from OpenAPI schema definitions

**Interface Naming:** `{Visibility}:{ApiName}:v{MajorVersion}:RestAPI`
- Example: `Private:Compute:v6:RestAPI`

### Example: REST API Multi-Stage Import

```yaml
# imports/rest-api.yaml
apiVersion: architecture/v1alpha1
kind: Import
metadata:
  name: Import:RestApi:Index
  annotations:
    import/handler: rest-api-index
    import/priority: "1"
    import/cacheTime: "24h"
    import/config/indexUrl: https://api.example.com/index.json
    import/config/interfaceOutputPath: generated/rest-api-interfaces.yaml
    import/config/dataObjectOutputPath: generated/rest-api-data-objects.yaml
    import/config/skipVisibility: public-preview
spec: {}
```

After running, this generates child imports like:

```yaml
# generated/Import_RestApi_Index.yaml
---
apiVersion: architecture/v1alpha1
kind: Import
metadata:
  name: Import:RestApi:compute
  annotations:
    import/handler: rest-api
    import/config/name: compute
    import/config/version: "6.0"
    import/config/visibility: private
    import/config/specUrl: https://api.example.com/rest-api/compute/openapi.yaml
    import/config/htmlUrl: https://api.example.com/rest-api/compute/redoc.html
    import/config/gate: GA
    import/config/interfaceOutputPath: generated/rest-api-interfaces.yaml
    import/config/dataObjectOutputPath: generated/rest-api-data-objects.yaml
spec: {}
---
# Parent import tracks what it generates
apiVersion: architecture/v1alpha1
kind: Import
metadata:
  name: Import:RestApi:Index
spec:
  generates:
    imports:
      - Import:RestApi:compute
```

The dependency of `Import:RestApi:compute` on `Import:RestApi:Index` is automatically derived from the `generates` relation above.

## Multi-Stage Import Pattern

Imports can generate other Import resources, enabling multi-stage workflows:

1. **GitLab import** runs and discovers repositories
2. Generates `Import:Repo:*` for each repository
3. Database reloads, discovers new Import resources
4. **Repository imports** run concurrently (up to 20)
5. Each generates TechnologyArtifact resources
6. Loop continues until no pending imports remain

### Example: GitLab Multi-Stage Import

```yaml
# imports/gitlab.yaml
apiVersion: architecture/v1alpha1
kind: Import
metadata:
  name: Import:GitLab
  annotations:
    import/handler: gitlab
    import/priority: "1"
    import/cacheTime: "24h"
    import/config/host: gitlab.company.com
    import/config/repoOutputPath: generated/repositories.yaml
    import/config/fallbackTeam: "Team:Platform"
    import/config/corporateAffixes: "ionos,1and1"
spec: {}
```

After running, this generates:

```yaml
# generated/gitlab-imports.yaml
---
apiVersion: architecture/v1alpha1
kind: Import
metadata:
  name: Import:Repo:gitlab:company:my-service
  annotations:
    import/handler: repository
    import/config/path: ~/.cache/archsight/git/gitlab/company/my-service
    import/config/gitUrl: git@gitlab.company.com:company/my-service.git
    import/config/archived: "false"
    import/config/visibility: internal
    import/config/fallbackTeam: "Team:Platform"
    import/config/corporateAffixes: "ionos,1and1"
    import/outputPath: generated/repositories.yaml
spec: {}
---
# Parent import tracks what it generates
apiVersion: architecture/v1alpha1
kind: Import
metadata:
  name: Import:GitLab
spec:
  generates:
    imports:
      - Import:Repo:gitlab:company:my-service
```

The child import depends on `Import:GitLab` because the parent's `generates` relation includes it.

## Generated Annotations

### TechnologyArtifact Annotations

Repository analysis generates these annotations:

**Repository Info:**
- `artifact/type` - Always "repo" for repositories
- `repository/git` - Git URL
- `repository/visibility` - internal, public, open-source
- `repository/recentTags` - Recent git tags (releases)
- `repository/accessible` - "false" if repo couldn't be accessed
- `repository/error` - Error message for inaccessible repos

**Code Metrics (from scc):**
- `scc/languages` - Comma-separated language list
- `scc/estimatedCost` - COCOMO cost estimate
- `scc/estimatedPeople` - Estimated team size
- `scc/language/*/loc` - Lines of code per language

**Activity Metrics:**
- `activity/status` - active, abandoned, bot-only, archived, inaccessible, empty, no-code
- `activity/reason` - Explanation for non-standard statuses
- `activity/commits` - Monthly commit counts (12 months)
- `activity/contributors` - Monthly contributor counts
- `activity/contributors/6m` - Unique contributors (6 months)
- `activity/contributors/total` - Total unique contributors
- `activity/busFactor` - Risk assessment: high, medium, low
- `activity/createdAt` - First commit date
- `activity/lastHumanCommit` - Last non-bot commit date

**Deployment Detection:**
- `repository/artifacts` - Detected artifact types (container, chart, debian, rpm)
- `deployment/images` - OCI container image names
- `workflow/platforms` - CI/CD platforms (github-actions, gitlab-ci)
- `workflow/types` - Workflow types (build, test, deploy, etc.)
- `agentic/tools` - AI coding tools detected (claude, cursor, aider)

## Troubleshooting

### Deadlock Error

If you see "Deadlock: pending imports have unsatisfied dependencies", check that:

1. All dependencies exist as Import resources
2. Dependencies don't form a circular chain
3. Dependent imports haven't failed

### Access Denied Errors

When a repository can't be cloned due to access issues, the handler creates a minimal artifact with:
- `activity/status: inaccessible`
- `repository/accessible: false`
- `repository/error: <error message>`

This allows the import to continue processing other repositories.

### Cached Imports Not Updating

If an import isn't re-running when expected:
1. Check `import/cacheTime` annotation value
2. Check `generated/at` annotation on the Import resource
3. Use `archsight import --force` to bypass cache for all imports
4. Alternatively, use `import/cacheTime: never` to always re-run a specific import

**Note:** The cache is automatically invalidated when the output file is missing, the configuration or the inputs
changed, or a declared dependency executed (see [Caching](#caching)). Editing the Import definition invalidates it
only through its handler and `import/config/*` settings.

## Importers of the Resources Repository

A resources repository often needs importers that only make sense for it: deployments read from the repositories
archsight already cloned, a wiki space, team membership from a directory service. They live in the repository and
run with `archsight import` like the built-in handlers: scheduled with their dependencies, cached, filtered with
`-f`, shown by `-n` and checked by `archsight lint`.

### A Ruby handler

The Import names the handler and the file that registers it (`import/handlerPath`, relative to the resources
directory, like `import/outputPath`):

```yaml
# imports/deployments.yaml
apiVersion: architecture/v1alpha1
kind: Import
metadata:
  name: Import:Deployments
  annotations:
    import/handler: deployments
    import/handlerPath: importers/deployments.rb
    import/dependsOn: "Import:Repo:*"
    import/outputPath: generated/deployments.yaml
    import/cacheTime: "24h"
    import/config/inputs: "deployments/*.yaml"
spec: {}
```

```ruby
# importers/deployments.rb
require_relative "lib/charts" # helpers next to the handler

class DeploymentsImporter < Archsight::Import::Handler
  def execute
    progress.update("Reading charts")
    # the model as loaded after the dependencies ran
    components = database.instances_by_kind("ApplicationComponent")
    # the clones of the repository imports
    charts = Charts.find(File.join(cache_root, "github"))

    resources = charts.filter_map do |chart|
      next unless components.key?(chart.component)

      resource_yaml(kind: "TechnologyArtifact", name: "Chart:#{chart.name}",
                    annotations: { "artifact/type" => "chart" })
    end

    write_file("pages/deployments.md", Charts.page(charts)) # a page next to the generated YAML
    write_yaml(resources_to_yaml(resources) + YAML.dump(self_marker))
    write_generates_meta
  end
end

Archsight::Import::Registry.register("deployments", DeploymentsImporter)
```

- `import`, `lint` and `web` load the handler files the Imports declare. The resources repository is trusted like the
  gem: its handler code runs in all three commands.
- A name registered twice, a file that does not load or does not register the name in `import/handler`, and an
  unknown handler name are lint errors.
- Only the Ruby standard library and the gems archsight ships are available to a handler.
- Run it with what it depends on: `archsight import -f Import:Deployments`, or alone with `--no-deps`; see the plan
  with `-n`.
- A web server loads a handler file once; restart it after changing the file.

### A command in any language

`import/handler: command` runs a program instead:

```yaml
apiVersion: architecture/v1alpha1
kind: Import
metadata:
  name: Import:Wiki
  annotations:
    import/handler: command
    import/config/command: "python3 importers/wiki.py"
    import/config/env: CONFLUENCE_TOKEN
    import/config/requiredEnv: CONFLUENCE_TOKEN
    import/config/optional: "true"
    import/config/outputs: "pages/wiki/*.md"
    import/outputPath: generated/wiki.yaml
    import/cacheTime: "7d"
spec: {}
```

- The command line is split like a shell does, but runs without a shell (`sh -c '...'` for pipes). It runs in the
  root of the git repository that holds the resources directory (`import/config/workdir` relative to the resources
  directory overrides it).
- The environment is clean: `PATH`, `HOME`, `LANG`, `LC_ALL`, `TMPDIR`, the variables named in `import/config/env`, and
  - `ARCHSIGHT_RESOURCES_DIR` - the resources directory
  - `ARCHSIGHT_CACHE_DIR` - where the git-based imports clone repositories
  - `ARCHSIGHT_IMPORT_NAME` - the name of the Import
  - `ARCHSIGHT_OUTPUT_PATH` - a file for the YAML resources the program generates
- archsight writes what the program put in `ARCHSIGHT_OUTPUT_PATH` unchanged to `import/outputPath` and adds the self
  marker, so caching and dependencies work. The documents are not marked as generated: a document that only adds
  relations to a hand-written resource must not look generated, and many kinds (Location, TechnologyNode, ...) do not
  accept the `generated/*` annotations. A program that wants a resource marked sets `generated/script: <import name>`
  itself. Files matched by `import/config/outputs` are recorded as the import's own (see below).
- The output file belongs to the import: it is replaced on every run and removed when `import/outputPath` changes.
  `archsight lint` reports another import that writes to the same file.
- A non-zero exit fails the import with the last lines of the error output.

### Shared state and outputs

- `cache_root` (Ruby) and `ARCHSIGHT_CACHE_DIR` (command) are the directory the GitHub, GitLab and repository
  imports clone into: `import/config/cacheRoot`, else `import.cache_root` in the
  [configuration](configuration.md) (`ARCHSIGHT_IMPORT_CACHE_ROOT`), else `~/.cache/archsight/git`.
- `database` holds the model as loaded after the dependencies ran (the import command loads the kinds the importers
  use: Import, BusinessActor, ApplicationComponent, ApplicationInterface).
- `write_yaml` may be called several times with `filename:` for more YAML files next to the output path.
  `write_file(path, content)` writes a whole file of the import's own, such as a page. Its files are recorded in the
  self marker (`generated/outputs`): the cache is invalid while one is missing, and a file of an earlier run that is
  not written again is deleted. Call `self_marker` after writing them.

### Docker

The image runs `archsight import` with the repository mounted (`-v /path/to/repository:/resources`). Handler files
must be inside the mounted resources directory. The image has no git, go or python; a command import can only run
programs available in the image.

### Handler Helper Methods

| Method | Description |
|--------|-------------|
| `config(key, default:)` | Get a configuration value (`import/config/<key>`) |
| `config_path(key)` | Get a path setting with `~` expanded |
| `cache_root` | Directory of the cloned repositories |
| `database` | The model loaded before this batch of imports |
| `progress.update(msg)` / `progress.warn(msg)` | Update the progress display |
| `resource_yaml(kind:, name:, ...)` | Build a resource hash marked as generated by this import |
| `import_yaml(name:, handler:, ...)` | Build a child import hash (override `self.generates_imports?` to return true) |
| `resources_to_yaml(resources)` | Join resource hashes into YAML documents |
| `write_yaml(content, filename:, sort_key:)` | Write YAML to the output path (or a file next to it) |
| `write_file(path, content)` | Write a file of the import's own below the resources directory |
| `self_marker` | Marker with `generated/at` and the cache hashes; write it last |
| `write_generates_meta` | Record what the import generated (`spec.generates`) |
